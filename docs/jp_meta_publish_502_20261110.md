`http://10.61.20.5:14191/manager/api` 发布 `rbf_small` 时收到

## 结论与时间线

本次失败发生在 Manager 停止、重新启动及冷加载期间。Nginx 对
`127.0.0.1:18201` 的连接收到 `111: Connection refused`，对应的 POST
没有进入应用处理。发送端随后自行重试成功；本次没有重启或修改任何服务。

## 恢复验证

截至 03:47:15 UTC，恢复后的应用完成日志有 1,284 次目标请求，全部 200；
其中 `rbf_small` 213 次，全部 200，处理耗时中位数/P95/最大为
2/16/714 ms，最大应用排队时间为零。最近的 `rbf_small` 阶段日志确认完成
两个绑定账户的发布。这里的 HTTP 成功代表既有 Exec 发布确认语义，不代表
后台归档已经耐久落盘，也不证明每个曾失败的历史信号都被补发。

独立 Nginx 日志中，今天截至采样共有 427 次目标 POST 502，全部位于
03:32–03:36 的停服/启动窗口；最后一次是 03:36:04。恢复后没有新的目标
POST 5xx。今天另有 16 次目标 POST 499，发生在更早时段，不能用此次启动
原因解释，也不能声称所有历史超时已经消失。昨天还存在其他 502/499，
不在本次逐请求归因范围。

从原发送主机经原 URL 读取 `/auth/status` 返回 200，耗时约 66 ms；
Manager 主机本地经原 4191 Nginx 网关读取同一接口返回 200，约 2 ms。
使用禁用环境代理的 HTTP 请求，没有发送诊断交易目标。

当前 Manager 程序仍为 11 月 7 日 auth/session 发布二进制，SHA-256 为
`0d7f1b82ffba257690c66766d4352257fdb0dc500fde531501e5872cf6c5e90f`。
本次发现后台 PG 镜像存在超时重试告警，不能把它当成上述 TCP 连接拒绝的
原因；本次未通过受保护健康接口检查最终持久化队列状态。

## 尚未消除的启动空窗

当前 `src/web.rs` 的 `serve` 在首次 `build_dashboard(...).await?` 成功后
才构造完整状态并监听 HTTP。首轮历史读取和 NAV 重建因此延后正常目标接口
可用时间。此前将 SQL/RocksDB 写入移到独立后台队列的修复并未改变这个
启动顺序。服务停止到新进程启动之间的间隔也不属于 NAV 构建耗时。

后续若修改启动顺序，应让目标接口在必要的权限、会话、目标、绑定、费率及
账户模式检查就绪后开放，把分析初始化作为独立加载状态；必须保留归属修订
指纹等完整性检查，以及分析失败时的明确不可用状态。需要回归验证后再单独
部署，不能直接跳过检查或用 Nginx 自动重放 POST 隐藏失败。这样的修改只能
缩短冷加载窗口，不能消除单实例停止本身造成的中断。
