# jp-meta BNB 自动兑换与储备对冲恢复

2026-10-23，修复 `binance_exec_trade03`、`binance_exec_trade04` 的 BNB
自动管理阻塞，并按操作员确认恢复两账户 VIP2 储备对冲、更新 trade03 估算手续费。
保留已有门槛 25 BNB、触发线 25.2 BNB、补足目标 26 BNB；手续费钱包目标为
1.5 BNB，兑换上限为 10000 USDT 等值，常态对冲仍至少间隔一小时。

## 原因及代码修复

trade03 在 10 月 15 日 15:44:42 UTC、trade04 在 10 月 17 日 08:03:18 UTC
分别留下 `0.00006025`、`0.00008127` BNB 的赎回待核对记录。此前约 0.3 BNB
已从理财到账现货，但等待期间手续费继续消耗合约钱包，旧逻辑要求现货足额补到
1.5 才划转，因此又请求赎回极小尾差。trade04 当时日志明确返回 HTTP 400 /
`-6006`（低于最小赎回数量），程序仍按未知结果保留 pending，进而阻止后续补币。

以各账户重新核对过的交易 IP `172.31.35.228` 固定查询，从原请求前一小时直到
本次恢复的完整 BNB001 赎回历史，均只有前一笔约 0.3 BNB 的 `PAID` 记录，
没有 pending 对应的小额赎回。恢复前两账户总储备约为 24.8512、24.9285 BNB。

修复后先将已有现货 BNB 划入手续费钱包，最多划到目标值；下一轮重新检查正常
触发线，避免追逐持续扣费产生的微量差额。仅将 Flexible 赎回明确返回 HTTP 400 /
`-6006` 识别为确定拒绝，记入审计并清除本笔 pending。其他 HTTP 错误、超时、
响应丢失和未知结果仍保留 pending，不能自动重提。旧 pending 经历史核对后通过
Manager 的带时间戳 acknowledge 接口解除，未直接覆盖运行中的资金日志。

## 系统对冲修复

trade03 的 Redis 系统目标退回 10 月 9 日约 -5.7779567 BNB，事实空头约
-5.78 BNB；trade04 的系统目标及 index 条目缺失，但事实空头仍为 -25.99 BNB。
资金日志中两账户最后一次正常对冲目标均约 -26 BNB。操作员明确确认这些配置
损坏，并要求恢复两账户的 VIP2 储备管理。此次未确定目标丢失的历史原因；当前
Redis 后台持久化状态正常。

恢复前核对当前交易凭据与运行进程一致、交易所 BNBUSDC 无活动订单、Viz 就绪，
且两个执行族的目标和仓位账本均不存在其他 CTA 的 BNBUSDC 归属。仅短暂通过
Manager API 暂停两账户 BNB 自动管理；以同一个现行 Redis runtime JSON 格式，
对系统策略 config/index 作一次有备份的原子维护。事务比较所有已检查的配置和
账本原值，拒绝覆盖并发更新；不修改账本、不改其他策略目标、不调用 Exec Config
写接口、不写 Exec RocksDB。随后立即恢复原有自动管理设置，由 Exec 正常轮询
加载并执行。

trade03 的目标为 -25.99928866 BNB，trade04 为 -25.99944275 BNB。trade03
由 Exec 完成补空，其原约 0.002 BNB 系统平仓尾差由内部对敲正常归入储备策略。
trade04 由 Exec 接回已有空头，无需重复建立该仓位。最终两账户事实 BNBUSDC
空头均为 -25.99 BNB；Viz 显示执行完成、无活动订单，未成交尾量均小于既有
0.02 BNB 容差。正常归属校验和一小时对冲冷却保持不变。
