## 结论

隧道发生连接中断，自动恢复需要等 SSH 进程退出。el01 的 Manager、Nginx
和 PostgreSQL 持续运行，其他入口的目标请求仍被正常处理。

04:10 的目标没有进入 Manager 的目标归档，也没有对应的账户发布记录。
同策略 04:15、04:20、04:25 三轮也缺失。下一次成功是 04:30 的自然新信号，
并非补发旧信号。本次证据不支持将这次超时归因为 Manager 的 SQL、RocksDB
写入或发布排队。

## 隧道恢复机制

现有 unit 采用 `Restart=always`、`RestartSec=3`。外层 SSH 已配置
`ServerAliveInterval=30`、`ServerAliveCountMax=3` 和 `TCPKeepAlive=yes`。
但 ProxyJump 对应 SSH 配置的实际值是 `ServerAliveInterval=0`，没有
`ConnectTimeout`，不能把外层设置视为所有跳转连接都有同样的探测。

没有发现该网关的 HTTP 探活恢复 timer。systemd 的进程在线状态不能证明
端口转发能完成请求；本次进程退出前的不可用窗口没有被 HTTP 探活缩短。
现存日志不足以进一步确定哪个网络设备或哪一跳首先失效，也不足以精确
解释每一分钟的检测延迟；不能将跳板未配置 keepalive 单独认定为全部根因。

建议后续单独改进入口运维：给跳转 SSH 明确连接超时与保活，并对
`/manager/api/auth/status` 做有总超时的端到端 HTTP 探活。连续失败时，
结合独立入口的健康结果与冷却间隔，仅恢复该隧道；不以恢复入口为由
重启 Manager、交易、Viz、Config 或 Redis。探活不能发送目标或重放历史信号。
这些属于建议，本次没有修改或部署隧道配置。
