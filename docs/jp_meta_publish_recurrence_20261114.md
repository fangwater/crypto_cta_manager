## 已确认的剩余 CPU 争抢

### CPU24 同时运行两个 Manager

`cta_web` 初次审计的全部42个线程绑在 CPU24，后续可见线程增长到58个，
其中只有一个 Tokio 异步调度线程
（TID438576）。NAV Manager 的 systemd 服务也配置 `CPUAffinity=24`；
其 PID971432 的全部现场线程同样只允许使用 CPU24。后者的服务启动时间
为11月13日06:25:20 UTC；本次没有修改其服务或仓库。

调度跟踪在15:01:49测到 CTA 异步线程已经可运行，却等待 CPU448255 µs；
另有334069、297704、284760、233375 µs 等等待。CPU24 的49 Hz采样直接
捕获到该线程等待期间，CTA 自己的阻塞工作线程、独立 NAV Manager 及
短时 `sync_history` 正在占用这个核。不能再把 CPU24 描述为 CTA 独占核，
也不能把所有 `tokio-rt-worker` 都当成异步事件循环线程。

进一步的同一调度窗口计时给出直接证据：15:12:49，CTA异步线程等待
259080 µs；这同一个窗口内，独立NAV的 PID971432 / TID1035249
累计运行至少257689 µs。后者是按超过1 ms的运行片段求和，因此为下界。
两者不是来自不同时段的平均CPU对比。这证明共核已造成实际的发布线程
调度延迟，但该窗口没有捕获到新的HTTP502，不能追溯等同于14:55的故障。

CTA 的后台 NAV 重建通常每分钟使用约11–13秒墙钟；本轮多个完整秒内
CPU24 达100%。平均占用不高不能排除这些集中发生的争抢。
检查到的 cgroup 祖先没有 CPU 配额节流；四分钟 CPU 采样的 steal 为零。
这些证据支持实际的应用 CPU 竞争，不支持本轮把延迟归因于配额或
观察到的虚拟机 steal。

当前核心归属也不能仅凭 `ps` 的最后运行 CPU 判断：25–27分别仍有
account_monitor、exec-pre-trade、trade_engine 的固定绑定，28还与
delist_risk_server 共用。调查使用 root 只读枚举所有用户线程的实际
affinity，避免遗漏 Redis 用户或误占交易核心。没有根据“看起来空闲”
直接调整任何服务。

### 后台同步工作仍在异步线程执行

原生栈采样在 TID438576 上捕获到：

- `postgres::symbol_index_deltas`：每分钟扫描合约索引输入。
- Viz 的 JSON 解析，以及 `AllocationSnapshot::validate`。
- NAV 事件和 allocation 容器的释放、JSON Value 的释放。

对合约索引函数做入口/返回计时，两轮各八个来源的单次耗时为约0.6–40.1 ms，
最长一次墙钟40142 µs，其中 off-CPU1726 µs；说明绝大部分确为该异步线程
执行同步计算。当前 `NavSourceHistory::symbol_index_events` 把摘要代表记录
和整个保留事件窗口连接起来，`refresh_source_symbol_index` 在首个SQL await
之前同步完成每个来源的聚合。它不是仅对几个新成交做增量聚合。

这些几十毫秒操作是已经量到的次级延迟，不能单独解释3.9秒故障。
Viz JSON 和旧对象释放的栈采样也只证明执行位置，未给出单次耗时，
不能据此宣称它们各自阻塞了两秒。

## Redis、文件系统与接口的对照

四分钟 TCP/syscall 跟踪覆盖8969次 Manager 到 Redis 的发送：
请求到 Redis `tcp_sendmsg` 入口的回复间隔均在4 ms以下，绝大多数为8–16 µs；
服务端回复到客户端读取最多落在8–16 ms桶。此处是 TCP 观察，不是完整
HTTP延迟，也不是每个业务请求的一一对应计时。
这轮没有记录到超过10 ms的 Redis write/fsync/fdatasync。
共享文件系统 journal 线程的 runnable 等待均落在4 ms以下。
与早先1.196秒 journal CPU等待相比，本轮没有重现同样的存储长尾。

独立的15:04:38–15:08:38观察结果：

| 只读探针 | 数量 | 最大耗时 |
| --- | ---: | ---: |
| Redis PING | 2398次成功 | 3.478 ms |

探针单独记录自身调度迟到，最大24.939 ms，不能把该值算成 Redis处理耗时。

ERR6 / NOPERM1 保持既有值，delayed-fsync累计仍为3，AOF写入/重写状态正常。

`spread_bbo_zmq_pub` 是持续占用者之一；其他行情、FR和系统任务也在

本轮 journal 延迟已明显缩短，因此这是剩余容量问题，不能直接重新套用
早先的慢fsync因果链解释本次失败。

PG 的一次只读现场采样有四个 idle 客户端连接，未观察到等待锁的活动业务

故障时的PG等待。归档/PG队列的完整健康状态需要受保护健康接口；匿名
探针没有取得它们，不应将“没有持续告警”等同于队列已耐久清空。

## 修复顺序与结论边界

### 后续只读审查：独立NAV本身也存在计算优化空间

操作员进一步询问NAV耗CPU是否因为缺少优化。审查独立
`crypto_nav_manager` 的现行源码及生产二进制后，确认已有结果缓存、
五分钟刷新门槛、单个历史重算信号量及阻塞线程上的FIFO重放，不能说它
完全没有优化。但这些措施没有消除下面的重复计算：

- `src/server/fr_overview.rs` 的 `reconstruct` 每次仍从初始快照或配置历史
  起点调用 `pnl::load_inputs`；之后重新排序并FIFO重放。46天只限制输出
  点的时间范围，不会把此前建立持仓所需的历史变成增量检查点。
- `src/pnl.rs` 的 `SymbolState::apply_trade` 每笔成交后都对现货、期货
  调用 `snapshot`。`src/quantity_fifo_pnl.rs` 的 `snapshot` 每次遍历全部
  未平仓批次求浮盈。若未平批次数随成交累积，这部分总工作量可接近平方
  增长；不是所有账户都必然达到这个最坏情况。

这项判断也有实际热点证据：将先前 `competition.txt` 中NAV工作线程的
六个热点指令地址，按仍在运行的PID971432的ELF映射和生产符号表解析，
都落在 `QuantityFifoPnl::snapshot` 内遍历 `VecDeque<Lot>` 并求和的同一
编译函数中。该采样只针对CTA等待期间，不能据此给出整个NAV进程的CPU
占比，也没有给15:12:49那259ms的每条指令做独立归因。

后续算法优化应保持FIFO配对与财务口径，维护数量/成本汇总以降低反复估值
开销，再增加可校验的增量检查点及迟到/修订数据失效重算机制。CPU隔离
保护实时发布，算法优化减少实际计算量，两者解决的问题不同。本轮没有
修改NAV业务代码、其已有README工作区修改或生产服务。

优先审查前台发布、CTA分析、独立NAV与短时历史工具的CPU归属，使耗时工作
不能持续争用发布所在的单核。选核心前保留全机实际 affinity 审计，不能
占用交易核心，也不能仅移动 Redis 后便认为依赖已隔离。两个 Manager
继续保持独立部署和数据所有权。

随后将索引聚合、较重的 JSON 解析和大型旧代释放移出异步调度线程，
并限制后台并行工作对前台的影响。索引可使用已经维护的首事件/首成交/
末成交摘要，但需要保持来源、symbol、venue边界和历史时间的正确性。
不要降低 WAL/AOF 耐久性，或单纯加长两秒超时掩盖调度延迟。

仍缺少14:55:09故障时同步的用户栈、TCP和kernel跟踪，因而本次已确认
上述剩余瓶颈，但没有证明其中某一项就是那一次3.9秒等待的唯一原因。
下一轮复发应同时对照事件循环延迟、线程调度、Redis请求/回复和fsync，
不能把错误字符串中的Redis当成已证实的服务端根因。

本地忽略的诊断脚本与脱敏证据位于
`artifacts/rbf_big_recurrence_20261114/`。此前FR04和journal调查见
`jp_meta_rapidx_monitor_20261114.md`；Redis恢复修复见
`jp_meta_redis_upgrade_20261114.md`。

15:15:25 UTC收尾复查：CTA、Redis、NAV的上述PID保持不变，三个服务均为
active、`NRestarts=0`；rbf_mid/rbf_big最新请求均在15:15:24返回200、处理1 ms。
15:10:46以来未见新的账户发布失败或目标持久化延迟告警。所有本轮BPF
跟踪均已退出，没有遗留跟踪进程。此次仅增加调查文档，未修改业务代码。
