## 原因定位与边界

证据高度指向 Manager 同步推送的全局串行处理与发送端等待期限冲突。
`src/web.rs::save_position_strategy` 从函数开始到响应返回一直持有
`configuration_lock`。在锁内读取目录、保存 PostgreSQL、逐来源拉取 Viz
实际仓位、写入归档，再逐账户执行 `publish_binding_with_projection`。
多个策略同一信号时刻到达时，后到请求必须等待前面策略完成所有账户。
任何一个账户处理变慢都会占用整条队列；重试又加入相同队列。

每账户发布还调用 `exchange_leverage::has_required_trading_account_mode`。
对 native Binance STANDARD 路径，该调用新建 HTTP 客户端并同步等待
签名 `/fapi/v1/accountConfig` 查询，单次超时上限 10 秒；UNIFIED 路径不发此请求。
仓位归档的 Viz 请求超时为每来源 5 秒。两处等待都位于全局锁内。
当前日志没有锁等待、Viz、账户模式校验、Redis 的分阶段耗时，因此不能
进一步把当时的首个慢调用确定为某个 Viz、Binance 请求或 Redis 操作。
也没有发送端原始日志来精确核对每次请求开始时间和 timeout 秒数。

告警名称虽写“Exec Config”，当前目标下发代码实际通过 Manager Redis 写入
及 reload notify 完成；单凭告警不能认定 Exec Config HTTP 服务超时。

## 修复方向

1. 记录请求 ID、策略名、锁等待及各阶段耗时，网关记录 request/upstream time。
   避免记录 token、完整目标或认证信息。
2. 将无关策略的推送隔离，缩短全局配置锁覆盖范围；保持同策略更新顺序、
   授权检查、份额与归档一致性，避免简单删除锁导致旧目标覆盖新目标。
3. 对账户模式校验及仓位读取做受控复用/并发，保留正确性与来源隔离；
   将已接受目标的发布生命周期与 HTTP 客户端断开解耦，并能确认部分失败和重试。
4. 发送端的超时和重试间隔需按真实端到端耗时配置；仅提高 Nginx 的 180 秒
   超时不能解决客户端先断开的问题。先核对实际客户端参数，不据仓库示例
   的默认 5 秒推断生产值。

本次未修改业务代码、目标、绑定或服务配置，未重放旧信号、未重启服务。
仅创建一个五分钟诊断登录会话访问只读 API，在 `finally` 删除并确认不存在。
凭据未输出。诊断脚本、归档摘要、成功下发时间线和源文件比对结果保存在
`artifacts/el01_publish_timeout_20261105/`。
